## 인덱스란?

**인덱스(index)**는 SELECT를 사용해서 테이블을 조회할 때 결과를 빠르게 추출하도록 도와주는 기능. 실무에서는 현실적으로 인덱스 없이 데이터베이스 운영이 불가능함.

> 💡 인덱스를 만들면 SELECT 문의 출력 속도가 빨라짐.

---

## 인덱스의 장점과 단점

인덱스는 SELECT에서 즉각적인 효과를 내는 빠른 방법 중 한 가지. 적절한 인덱스를 생성하고 사용하는 SQL을 만든다면 기존보다 아주 빠른 **응답 속도**를 얻을 수 있음. 
**장점**
- SELECT 문으로 검색하는 속도가 매우 빨라짐
- 그 결과 컴퓨터의 부담이 줄어들어서 결국 전체 시스템의 성능이 향상됨

**단점**
- 인덱스도 공간을 차지해서 데이터베이스 안에 추가적인 공간이 필요함
  > 인덱스는 대략 테이블 크기의 10% 정도의 공간이 추가로 필요함
- 처음에 인덱스를 만드는 데 시간이 오래 걸릴 수 있음
  > 찾아보기가 없는 책에 새로 찾아보기를 만드는 것과 마찬가지로 작업 시간이 필요함
- SELECT가 아닌 데이터의 변경 작업(INSERT, UPDATE, DELETE)이 자주 일어나면 오히려 성능이 나빠질 수도 있음

---

## 인덱스의 종류

- **보조 인덱스**: 찾아보기가 별도로 있고, 찾아보기에서 해당 단어를 찾은 후 옆에 표시된 페이지를 펼쳐서 실제 내용을 찾는 것
- **클러스터형 인덱스**: 영어사전처럼 책의 내용이 이미 알파벳 순서대로 정렬되어 있는 것. 별도의 찾아보기가 없음 (책 자체가 찾아보기)

> 💡 인덱스는 클러스터형 인덱스(영어사전)와 보조 인덱스(일반 책의 찾아보기) 두 가지가 있음.

---

## 자동으로 정렬되는 클러스터형 인덱스

클러스터형 인덱스는 기본 키로 지정하면 자동 생성되고, 테이블에 1개만 생성됨. 이번엔 **클러스터형 인덱스의 정렬 특징**을 확인함.

- 영어사전의 가장 큰 특징: 단어가 알파벳 순서로 정렬되어 있음
- 어떤 열을 기본 키로 지정하면(클러스터형 인덱스가 생성되면) **그 열을 기준으로 자동 정렬**됨

### 실습 - mem_id를 기본 키로 지정 후 확인

```sql
ALTER TABLE member
    ADD CONSTRAINT
    PRIMARY KEY (mem_id);
SELECT * FROM member;
```

| mem_id | mem_name | mem_number | addr |
|---|---|---|---|
| BLK | 블랙핑크 | 4 | 경남 |
| OMY | 오마이걸 | 7 | 서울 |
| TWC | 트와이스 | 9 | 서울 |
| WMN | 여자친구 | 6 | 경기 |

→ mem_id 열에 클러스터형 인덱스가 생성되어 **mem_id 기준으로 자동 정렬**됨 (알파벳 순).

### 기본 키를 다른 열로 변경하기

mem_id의 Primary Key를 제거하고, mem_name 열을 Primary Key로 지정하면? (영한사전을 한영사전으로 바꾸는 개념)

```sql
ALTER TABLE member DROP PRIMARY KEY ;        -- 기본 키 제거
ALTER TABLE member
    ADD CONSTRAINT
    PRIMARY KEY(mem_name);                    -- 클러스터형 인덱스 생성
SELECT * FROM member;
```

| mem_id | mem_name | mem_number | addr |
|---|---|---|---|
| BLK | 블랙핑크 | 4 | 경남 |
| WMN | 여자친구 | 6 | 경기 |
| OMY | 오마이걸 | 7 | 서울 |
| TWC | 트와이스 | 9 | 서울 |

→ 데이터 내용 변경은 없으나, **mem_name 열 기준으로 재정렬**됨 (mem_name에 클러스터형 인덱스가 생성되었기 때문).

이후 데이터를 추가 입력하면 자동으로 기준에 맞춰 정렬됨.

> 💡 클러스터형 인덱스는 테이블에 1개만 생성할 수 있음. 기본 키가 테이블에 1개인 것과 마찬가지임.

---

## 정렬되지 않는 보조 인덱스

고유 키로 지정하면 보조 인덱스가 생성됨. 보조 인덱스는 테이블에 **여러 개** 설정할 수 있음 (고유 키를 여러 개 지정할 수 있는 것과 마찬가지).

보조 인덱스는 일반 책의 찾아보기에 비유됨. 찾아보기를 만들면 책의 **뒤에 추가**되는 것이지 **책 본문이 변경되는 것은 아님**. 찾아보기를 만든다고 해서 본문의 순서나 내용이 바뀌지 않음.

### 실습 - mem_id를 고유 키로 설정

```sql
ALTER TABLE member
    ADD CONSTRAINT
    UNIQUE (mem_id);
SELECT * FROM member;
```

→ 결과는 **입력한 순서 그대로** (변화 없음). 보조 인덱스를 생성해도 데이터의 순서는 변경되지 않고 별도로 인덱스만 만들어짐.

> 💡 보조 인덱스를 생성해도 데이터의 내용이나 순서는 변경되지 않음.

### 실습 - mem_name에 추가로 고유 키 지정

고유 키는 여러 개 설정해도 되므로 기존 고유 키를 제거할 필요 없음.

```sql
ALTER TABLE member
    ADD CONSTRAINT
    UNIQUE (mem_name);
SELECT * FROM member;
```

→ 역시 데이터의 내용과 차례는 그대로. 현재 mem_id 열과 mem_name 열에 모두 보조 인덱스가 생성된 상태.

데이터를 추가 입력하면? (일반 책에 새로운 내용이 추가되면 본문 제일 뒤에 추가되는 것과 동일)

```sql
INSERT INTO member VALUES('GRL', '소녀시대', 8, '서울');
SELECT * FROM member;
```

| mem_id | mem_name | mem_number | addr |
|---|---|---|---|
| TWC | 트와이스 | 9 | 서울 |
| BLK | 블랙핑크 | 4 | 경남 |
| WMN | 여자친구 | 6 | 경기 |
| OMY | 오마이걸 | 7 | 서울 |
| GRL | 소녀시대 | 8 | 서울 |

> 💡 보조 인덱스는 여러 개 생성할 수 있음. 고유 키를 테이블에 여러 개 지정하는 것과 마찬가지임.

## 마무리 - 3가지 키워드 핵심 정리

| 키워드 | 설명 |
|---|---|
| **클러스터형 인덱스** | 영어사전처럼 내용이 이미 정렬되어 있는 인덱스. 기본 키로 지정하면 생성되고 해당 열로 자동 정렬됨 |
| **보조 인덱스** | 일반 책의 찾아보기와 같이 별도의 공간에 인덱스가 생성됨. 고유 키로 지정하면 생성되고 자동 정렬되지 않음 |
| **고유 인덱스** | 값이 중복되지 않는 인덱스. 기본 키나 고유 키로 지정하면 값이 중복되지 않아서 고유 인덱스가 자동 생성됨 |

## 2. 인덱스의 내부 작동 

## 핵심 키워드
`균형 트리` `페이지` `전체 테이블 검색` `페이지 분할` `인덱스 검색`

---

## 균형 트리란?

클러스터형 인덱스와 보조 인덱스는 모두 내부적으로 **균형 트리(Balanced tree, B-tree)**로 만들어짐. 균형 트리는 '자료 구조'에 나오는 범용적으로 사용되는 데이터의 구조.

나무를 거꾸로 표현한 자료 구조로, 트리에서 제일 상단의 뿌리를 **루트**, 줄기를 **중간**, 끝에 달린 잎을 **리프**라고 부름.

> 💡 인덱스는 균형 트리의 자료 구조로 구성되어 있음.

---

## 균형 트리 개념

균형 트리 구조에서 데이터가 저장되는 공간을 **노드(node)**라고 함.

- **루트 노드(root node)**: 노드의 가장 상위 노드. 모든 검색의 출발점
- **리프 노드(leaf node)**: 제일 마지막에 존재하는 노드
- **중간 노드(internal node)**: 루트 노드와 리프 노드 사이에 끼인 노드 (데이터가 많으면 3단계 이상도 가능)

> 📝 노드라는 용어는 개념적인 설명에서 주로 나오는 용어이며, MySQL에서는 **페이지(page)**라고 부름. 페이지는 최소한의 저장 단위로, **16Kbyte(16384byte)** 크기를 가짐. 데이터를 1건만 입력해도 1개 페이지(16Kbyte)가 필요함.

---

### 인덱스 검색

균형 트리는 무조건 **루트 페이지**부터 검색함. 모든 데이터가 정렬되어 있으므로, 원하는 데이터가 속한 리프 페이지로 바로 이동 가능. MMM을 찾을 때 루트 페이지 1개 + 해당 리프 페이지 1개, 총 **2페이지만 읽어서** 결과를 얻을 수 있음.

→ 인덱스가 없으면 3페이지를 읽어야 했지만, 균형 트리(인덱스)를 사용하면 2페이지만 읽어도 됨.

> 📝 몇 건의 데이터를 읽었는지가 아니라, **몇 개의 페이지를 읽었는지**로 효율성을 판단함.

---

## 균형 트리의 페이지 분할

인덱스를 만들면 SELECT의 속도를 향상시킬 수 있음(2페이지 읽기 vs 3페이지 읽기). 그런데 인덱스를 구성하면 **데이터 변경 작업(INSERT, UPDATE, DELETE)** 시 성능이 나빠짐. 특히 INSERT 작업이 느려지는 이유는 **페이지 분할**이라는 작업이 발생하기 때문.

**페이지 분할**: 새로운 페이지를 준비해서 데이터를 나누는 작업. 페이지 분할이 일어나면 MySQL이 느려지고, 너무 자주 일어나면 성능에 큰 영향을 줌.

---

## 인덱스의 구조

**클러스터형 인덱스 구조**

- 데이터 페이지(리프 페이지)가 mem_id 기준으로 정렬됨
- 각 페이지의 인덱스로 지정된 열의 **첫 번째 값**을 가지고 루트 페이지를 만듦
- 클러스터형 인덱스는 루트 페이지와 리프 페이지(+중간 페이지)로 구성되며, **리프 페이지가 곧 데이터 그 자체**

> 💡 클러스터형 인덱스를 구성하면 데이터 페이지도 인덱스에 포함됨. 영어사전의 본문이 찾아보기의 일부라는 것과 같은 개념.

**보조 인덱스 구조 (차이)**

- 보조 인덱스는 **데이터 페이지를 건드리지 않음** — 데이터 페이지는 그대로 입력 순서 유지
- 별도의 장소에 **인덱스 페이지**를 새로 생성함
- 인덱스 페이지의 리프 페이지에는 인덱스로 구성한 열(mem_id)이 정렬되어 있고, 실제 데이터 위치는 **페이지 번호 + #위치**로 기록됨 (예: APN → `1001+#4` = 1001번 페이지의 네 번째 위치)

> 💡 보조 인덱스를 구성하면 인덱스가 별도의 공간에 만들어짐. 일반 책의 찾아보기가 책 뒤에 별도로 만들어지는 것과 같은 개념.

---

### 결론

**인덱스 검색(Index Scan)**을 통해 두 인덱스 모두 검색이 빠르긴 하지만(전체 테이블 검색보다), **클러스터형 인덱스가 보조 인덱스보다 조금 더 빠름**. 클러스터형 인덱스는 리프 페이지 자체가 데이터이므로 한 단계를 덜 거치기 때문.

## 마무리 - 5가지 키워드 핵심 정리

| **균형 트리** | 나무를 거꾸로 표현한 자료 구조. 인덱스는 내부적으로 균형 트리로 구성됨 |
| **페이지** | 트리 구조에서 데이터가 저장되는 공간(노드)을 MySQL에서 부르는 명칭 |
| **전체 테이블 검색** | 데이터를 처음부터 끝까지 검색하는 것. 인덱스가 없으면 전체 페이지를 검색하는 방법밖에 없음 |
| **페이지 분할** | 데이터를 입력할 때 입력할 페이지에 공간이 없어서 2개 페이지로 데이터가 나뉘는 것 |
| **인덱스 검색** | 클러스터형 또는 보조 인덱스를 이용해서 데이터를 검색하는 것. 인덱스를 사용하지 않았을 때보다 속도가 빠름 |
